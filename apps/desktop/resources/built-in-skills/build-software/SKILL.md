# Build and check the requested software

Match the build to the requested outcome and its done condition. One best-fitting software owner plans and implements the whole result, using focused help when needed; use delegate for profile and model choice. Add a separate lead only when several owners need continuing coordination. Keep code, setup steps, decisions and evidence in the assigned project folder, and keep previews apart from deliverables. A review-only request returns findings without inventing an implementation. Make the owner responsible for a reproducible result: enough setup and configuration to run it, a clear way to observe success, and a way to recover from expected failure. The checker should exercise behavior from the user's perspective rather than merely reading the same code. Choose checks proportionate to risk; one small script may need a dry-run and edge-case check, while a larger app may need several flows. Do not add a lead or extra profiles simply because code is involved.

Any script or command that changes, moves or deletes the person's files, however small, needs an owner and independent checker. Make a preview or dry-run the default, preserve originals, and test on copies before asking the person to run it on real files. Do not overwrite or delete their originals without authorization. Read-only explanations and snippets may stay in chat.

The independent checker tests the running result against the done condition and important failure paths, using checks suited to the app, script or server. Record what was tested and what happened. Fix a failed check and check the correction. Every checker finding is either fixed and re-checked or named in the handback with why it remains, for the giver to decide. The owner must not reclassify a finding as an acceptable limit alone. If implementation changes after the independent check, send those changes back to the checker or identify them plainly as unchecked in the handback. The giver decides whether unchecked work meets the agreed outcome.

A build or change is ready only when it runs and has been checked as agreed. Tell the caller how to start, stop and maintain it when relevant, plus known limits and untested paths. Keep reproducible instructions and evidence on the piece. For a missing connection, follow add-a-capability for reviewed setup and the current server-request tool; do not invent registration or approval. The person handles every sign-in and approval. If a required helper or permission is unavailable, complete only permitted work and report precisely what prevents the done condition.

# Plugin lifecycle controller

The global supervisor owns `PluginLifecycleController`. `createSupervisorLifecycle` joins the global journal, verified archive vault, real supervised Node host, consumer hooks and the private person-control service. `bootstrapPluginLifecycle` is the immutable launch adapter. It verifies the nonempty signed catalogue before opening state or exposing control. `connectPluginSettings` adapts that separate capability to the existing Settings controller interface. The production controller supplies a trusted lifecycle plan only after a build-pinned, nonempty catalogue verifies. The committed key/source slots are empty, so the tab stays hidden and ordinary agent work is unchanged; see `plugin-production.md`.

## Person authority and bounds

The app's trusted main process supplies one distinct random 256-bit person-control key. It is not a workspace lease, an agent identity, a broker token, or a renderer argument. The reviewed lease protocol still accepts only hello/renew/release. The private owner-only Unix socket sends a fresh challenge; HMAC-authenticated packets bind that challenge, direction and strictly increasing counters. Captured packets cannot be replayed into a new session. Wrong keys and malformed, oversized, extra-field and unknown commands refuse. No command supplies package paths, keys, executables, environment, arbitrary URLs or arbitrary process RPC. There are at most 64 connections, 8 incoming and 8 outgoing requests per connection, 16 KiB per packet, 64 KiB per buffered batch, a 2-second initial authentication window and a 30-second request deadline. Overflow closes admission rather than truncating a snapshot. The person key and process endpoint credentials never reach plugin pages, agent instructions, broker calls, error messages or proof outputs.

The authenticated workspace UUID binds an opaque controller handle and its reverse cleanup hooks. The caller supplies real broker/UI cleanup adapters; their promises must acknowledge actual quiescence, not only request it. The Settings adapter denies its UI synchronously before awaiting destruction. UI teardown now returns the host's actual close promise, including isolated storage cleanup. A failed or disconnected cleanup is not successful removal. A closed connection is not exit evidence. The owner also waits for outstanding person commands and refuses a clean shutdown with a pending mutation or unresolved cleanup. The actual Settings handler dispatches Uninstall before reading the catalogue or awaiting view teardown, invalidates its generation, and settles both operations independently. UI failure cannot suppress denial/tombstoning, but success still requires actual teardown proof. The existing owner drain deadline keeps application quit bounded while retaining an uncertain ownership fence.

## Clean quit with an installed plugin

The production facade denies new calls immediately, cancels catalogue I/O separately, and keeps person control alive until detach and reverse revoke acknowledgments finish. It then closes the channel before releasing the workspace lease. Owner drain marks intentional shutdown before concurrent child stops and still requires positive exit from each exact run. Unexpected or unproved exits retain cleanup-pending and fence replacement. A clean quit preserves the activation and global workspace receipt; the next owner reloads the verified vault, starts a fresh run, awaits readiness and reports Running.

`plugin-shutdown.test.ts` covers installed quit and fresh-owner restart, a host exit before delayed consumer cleanup, unexpected exit denial/revocation, and an unproved drain. `plugin-production.test.ts` also checks live-channel detach ordering and cancellation of pending catalogue I/O. These controls use private scratch roots and inert process peers; they do not launch the app or Chrome.

## Install and interruption

Download uses credential-free HTTPS, no redirect, identity transfer encoding, a 30-second abort signal and the signed exact archive size (also capped by verifier limits). Verify the catalogue signature, immutable historical release pins, target, archive, manifest and payload digests before mutation. A reinstall also checks retained data schema against the new package's compatibility range. No package-manager install, hook or shell runs.

Persist exact structured consent and installation UUID in the global journal, stage the verified immutable archive, register the exact host run with the supervisor, and require authenticated readiness. Before prepare, freeze the live workspace cohort in the journal request. The existing prewritten complete/abort records now cover its empty receipts as part of that same resolution. With authenticated readiness and the global pending barrier still active, apply and acknowledge every required workspace binding. Persist the completion effect marker, recheck the cohort is still live, then atomically publish activation and all cohort receipts in the one pre-reserved completion record. No post-activation receipt record or compensating fresh uninstall is needed. Packages declaring any skills are refused with `Plugin unavailable. Try again.` before prepare, staging or start. Plugin skill projection is deferred to the later shared-skills integration; this slice changes no skill catalogue or selection store. Completion markers and verified package-cache bytes are private and kept current outside restore sets. A retry cannot invent another identity or change pinned release bytes.

An ordinary failed first install stops the exact run and revokes consumers before removing immutable code/cache and publishing its already-reserved abort. Receipt application happens before activation, so its failure cannot require a new uninstall operation. A verified journal completion is the commit boundary: losing a response after it keeps the complete installation/receipts rather than undoing them. The effect marker alone is never activation authority; recovery still resolves a pending journal operation even when that marker says committed. Never undo a later installation. Recovery examines durable completion markers and guards: incomplete operations unwind only with the newly fenced owner's clean predecessor proof. Unknown host/consumer exit retains a denying floor, code and ownership fence; it is never converted into an invented success. Successful recovery clears only its own still-current admission block after durable resolution/effect completion and positive cleanup; uncertain cleanup retains denial. Missing history is not initialized as empty. The state birth marker also prevents reinitializing a guard removed after an earlier initialization attempt.

## Uninstall and receipts

Deny calls synchronously before queueing. Journal the tombstone before stopping anything. Attempt every consumer/UI revocation and the exact host run stop independently; require positive exit and descendant proof, then remove only immutable code/cache and complete the operation. Published cache bytes are fully verified before a bounded same-parent rename to a private retirement name bound to operation UUID, install UUID and digest. The parent directory is fsynced before any recursive deletion, on the initial call and on retries. Partial retirement is an expected resumable state; only private regular immutable remaining files are deleted, without requiring an already-deleted archive. Partial/tampered published caches still refuse verification. Code retirement uses the same rename-before-delete rule. Profiles and downloads are never passed to deletion. Retrying an unfinished uninstall uses the same operation ID. No destructive data-delete API exists.

Canonical empty projection receipts are append-only `projected` records in the **existing global lifecycle journal**, keyed by `(workspaceId, pluginId)`. There is no workspace table, migration, provider-home write or second workspace database. They share the writer fence, checksums, tail-loss seals, limits and restore exclusions. Separate projection writes are refused while a lifecycle resolution is pending. New install/uninstall requests carry a bounded, unique cohort of at most 64 workspace UUIDs; receipt installation/removal is folded atomically with the reserved resolution, including record, encoded-byte and publication-name limits. Later attachments wait and cannot consume that reservation. Uninstall receipt removal is in its completion, after actual cleanup. Offline receipts stay as obligations: on reopen the mandatory adapter first revokes stale tool/UI bindings and acknowledges an uninstalled workspace projection. It includes tombstoned plugins even when the canonical receipt was already cleared. It may rebind only after checking the current owner installation, verified package, authenticated runtime readiness and a fresh adapter acknowledgment; then it records that new receipt. No restored local row or matching older global receipt preserves authority. Receipt data grants no admission on its own. Restoring a workspace cannot rewind this journal or resurrect A. Restore-aware broker/UI adapters must clear the actual workspace bindings on every attachment before any rebind, even if its canonical receipt matches. There is no continuity-preservation hook and no local install-identity marker. Plugin skills are unavailable until implemented on the shared-skills tree; no new local persistence is introduced here.

## Configuration read and integration limits

The bridge serves the verified package's own screen through the existing isolated host. Each binding contains an opaque UI scope identity (the host's `leaseId` field); it is never a supervisor lease capability. Fixed Chrome reads use the exact run's private authenticated admin capability for profiles and tabs and expose validated public fields only. Endpoint credentials remain in the owner. Reads recheck admission after await. For reviewed Chrome profile setup, the person's package-screen button confirms its bounded fixed action. Person control validates installation/incarnation and consumes a durable per-install page revision before calling create/enable/open admin endpoints; no second dialog or broker/agent route is added. `Installation.configRevision` remains reserved; see `plugin-production.md`. Subscription reads are bounded polls. Configuration control beyond Chrome requires a reviewed fixed adapter, never generic HTTP forwarding.

The committed production catalogue source list/key slot remain empty; the real controller is gated behind verified catalogue admission and connection. Trusted probes explicitly inject a fictional signed catalogue and inert consumer hooks. A launch-plan `downloads` list is a fixture/cache injection of archive bytes; it is not accepted over person IPC and those bytes still pass every signature/digest/manifest check. No such plan is supplied in production. The initial disk backend remains POSIX/main-thread only and fails closed on Windows. Runtime, host, launch, verification and storage failures affect plugin availability, not normal agents. SQLite journal capacity remains bounded with no compaction; exhaustion refuses safely without forgetting tombstones.

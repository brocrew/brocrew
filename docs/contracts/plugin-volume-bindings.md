# Plugin volume bindings across a reboot

macOS device numbers are mount assignments. Reboot proof identities and shared Chrome directory identities use the volume's persistent UUID and inode across launches; current-run revalidation still pins device and inode. The native reader queries Foundation's `NSURLVolumeUUIDStringKey` through a fixed, Foundation-only JavaScript script in the built-in `/usr/bin/osascript`. The path is passed as an argument, never script text. A fresh process and NSURL resolve the path's actual volume (including APFS Data-volume firmlinks); no AppleEvents/application access is used. This reads the same persistent UUID as `diskutil` without its per-call latency. Missing or ambiguous native identity refuses admission. Shared-profile operations cache one native observation per device only during a synchronous public operation (including nested reads), and clear it on return or throw. The next operation always observes the UUID again, even when device and inode match: replacing an anchored volume while preserving those values must still refuse. Explicit final revalidation during legacy enrollment remains fresh. Restore takes profile/identity/authorization together in one synchronous admission snapshot per check; every pre- and post-await check takes a fresh snapshot, with the existing identity, permission epochs, generation checks and five-second profile budget preserved.

On Windows, the packaged Node 24.22.0 libuv implementation fills `st_dev` from `VolumeSerialNumber.LowPart`. This is a formatted-volume serial, rather than a macOS mount assignment. Records qualify it as `winvol:<serial>`; a changed serial is refused, including for legacy records. The serial is not a hardware identifier and is not claimed to distinguish an exact filesystem clone. Linux retains its existing device/inode behavior; no new persistent-volume qualification is claimed there.

Sources: [Node's pinned Windows stat implementation](https://github.com/nodejs/node/blob/v24.22.0/deps/uv/src/win/fs.c), [Microsoft's formatted-volume serial contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationa), [Apple's persistent volume UUID](https://developer.apple.com/documentation/foundation/urlresourcekey/volumeuuidstringkey).

## Explicit legacy acceptance decision

Legacy records never saved a historical volume UUID. A same-path APFS clone or backup restore can preserve inode, owner, mode and type while changing the device number. Those observations cannot distinguish it from renumbering. The release owner explicitly accepts that ambiguity: restoring the same user's profile at the same location is intended behavior, and a user capable of replacing that filesystem already controls its files. This is a one-time enrollment policy, not evidence of historical volume continuity. Once recorded, a different persistent UUID always refuses.

For the shared registry, the implied profile/journal location must still contain the same inode, with no symbolic link, directory type, current-user ownership and private `0700` mode. Historical owner/mode fields are not invented. Whenever recorded, owner, mode, type, birth time and volume must match exactly. Accepted identities are replaced together under the existing registry mutex; each successful device rebind logs only `rebound after device renumbering`, after durable registry publication. Enrolling an unchanged device logs only `recorded durable volume identity`. No Chrome contents are read, copied, rebuilt or deleted. Moved journals follow the original source inode to the rename destination; another owner's home is enrolled only when that owner opens its own store.

For a pending reboot proof, every inode and the complete binding/census must match, and legacy device drift additionally requires a genuinely changed native boot witness. The certificate records durable identities and the original marker remains immutable. Existing completed certificates already contain the boot transition proving the old processes gone: a private, immutable enrollment binds their exact digest to durable directory identities. Later replay checks that enrollment, so a second device renumbering works and a changed recorded volume refuses. New run directories remain outside older certificates.

The app bundles reboot-proof recovery; the shared registry has one writer, the standalone Chrome plugin. Delivery therefore requires both the app release and the Chrome plugin release from the reviewed source. An app release alone does not distribute changed Chrome package code.

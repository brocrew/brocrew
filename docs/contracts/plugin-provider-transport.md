# Managed plugin transport

Managed plugin routes are distinct from the person's existing external-MCP registry. An absent `managedPluginMcp` field leaves both adapters unchanged. A supplied route is rebuilt for each start/resume: Claude receives HTTP `headers`; Codex receives per-thread `http_headers`. The adapters do not write the plugin's own credential into a provider home; native providers may retain their scoped broker configuration. Namespace collisions refuse rather than replace the app server or a registry entry. Provider-owned MCP/plugin discovery stays excluded by the existing pins.

`openManagedPluginRoute` binds one loopback endpoint to one opaque broker agent capability, installation and epoch. The process mints a new 256-bit bearer for that route; it is not the plugin's credential and authorizes no person/admin surface. Authentication, Host and Origin are checked before request-body reading or MCP initialization. Missing/wrong/cross-caller credentials and revoked handles fail closed. Requests cap at 64 KiB. Tools/list uses the broker's curated inventory; tools/call uses the same broker capability and qualified tool name, so resources, fairness and deadlines remain enforced. Resources, prompts and admin are not advertised. Stateless MCP cancellation notifications are mapped to active request IDs within that authenticated route; duplicate active IDs refuse. Route closure revokes its agent and closes owned streams/connections.

`createPluginCredential` generates 32 random bytes as exactly 64 lowercase hex characters; `createPrivatePluginPort` refuses every other length or alphabet. The port holds the plugin credential only in a private closure and speaks authenticated Streamable HTTP to a configured loopback endpoint. Redirects are refused. The provider receives only the per-launch broker bearer. Downstream response streams are byte-capped before decoding; raw exceptions are suppressed. Decoded reply strings and object keys containing the exact private credential fail closed, including successful content or nested metadata; this check does not rely on JSON escaping. No transport logger accepts raw requests, replies, credentials or error objects. Curated plugins still run with user rights; this is not a general malicious-plugin exfiltration sandbox.

Tool results require a natural terminal reply and owned client/stream closure before quiescence. Closing a cancelled/failed connection is not proof the remote operation stopped: that path rejects quiescence and the core makes the epoch unavailable. No successor is admitted on a guessed cancellation receipt. This layer proves request/transport completion, not process or browser-descendant exit; the later supervisor owns those gates.

The streamed surface here is MCP Streamable HTTP/SSE tool replies, followed by each provider's normal model streaming; no incremental tool-content API or progress-notification forwarding is introduced. The transport does not install plugins or attach RuntimeHost automatically. The host supplies live routes through the optional runtime field.

## Provider readiness and verification

Before the first Codex turn, supplied managed plugin routes get a readiness wait of up to ten seconds on that thread. A failed or slow plugin does not prevent the turn from starting; an unavailable result produces a bounded diagnostic without raw provider errors. Cancellation stops the waiting turn. Claude keeps its existing start behaviour.

Local controls use loopback HTTP/SSE with an inert plugin and fake provider entry points, plus the actual adapters' fake start/resume controls. They cover headers, isolation, revocation, resource denial, absent unsupported surfaces, namespace collisions and secret-bearing success/error replies. Readiness controls cover held discovery, failed servers, the wait bound and cancellation. These controls do not establish real CLI behaviour.

The native proof is a separate sealed check that is not included in this tree.

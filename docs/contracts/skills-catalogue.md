# Skills catalogue contract

Slices 1–2 on 135d61be1. One SQLite catalogue serves built-in, personal and plugin skills; plugin code must use this service. No UI, provider-home, launch/resume or native-capture changes here. Settings → Skills is the approved future destination. Reminder is an unprefixed instruction line, with help “A short line the agent sees at every turn.” Source text is never executed by the catalogue.

- **Identity/version:** IDs are `built-in/{name}`, `person/{name}`, `plugin/{pluginId}/{name}`. Names are immutable lower-case slugs, 1–64 characters. Rename creates another skill, initially off. Versions are immutable: personal Save generates v1/v2/…; built-ins use the verified shipped bundle version; plugins supply pinned release versions. A plugin version is scoped to its package version, allowing an unchanged skill release in a new package. Package version/digest pins cannot be replaced. Reusing a version with different bytes or metadata is refused. Selecting on/off/default survives version updates, app restarts and agent display-name changes.
- **Aliases:** built-ins retain native names. Other origins use `personal-` or `plugin-`, up to 24 name characters, and a 16-hex SHA-256 suffix of the complete origin-qualified ID. Store and verify this deterministic alias; refuse any collision. The later installer must project source frontmatter onto that alias and separately verify projected bytes; the original source/hash remains unchanged. No installer is delivered here.
- **Documents:** a single UTF-8 body at exactly `{name}/SKILL.md`, at most 65,536 bytes; exact declared byte count and SHA-256; one frontmatter name/description matching metadata; no other frontmatter keys. Description ≤500 characters; reminder ≤160, single-line; no hooks, commands, directory imports or supporting resources in this version. Duplicate IDs in a bundle, duplicate names within an origin, personal names shadowing built-ins, unsafe paths, invalid sizes/hashes and stale writes are refused atomically. Service failures are codes; a later person-only IPC maps them to approved UI words.
- **Defaults/grants:** built-ins on by default; personal/plugin skills off. Explicit choices attach to `agent_identity.id`, never a display name. Build-a-team needs agent creation; add-a-capability needs that grant or coordinator status, as today's shipped selection does. Other skill text never supplies capability grants. Resolution returns selection, eligibility and effective readiness separately; inactive plugin skills cannot become ready. No selected skill is a valid empty result. Bound the catalogue to 200 entries, pages to 50, selected views to 64 skills/4 MiB; refuse overflow rather than silently omit skills.
- **Publication/removal:** seed all eight verified shipped v23 definitions when initializing this service; do not rewrite their source texts. The service is not yet constructed by the app's UI/launch path. Same-bundle seeding is idempotent; changed bundled versions preserve choices and history. Person Save is an explicit edit and review, creating an immutable version. Plugin ingestion is a private boundary called only after the plugin manager verifies its signed package; the catalogue independently verifies every declared body/hash and records package version/digest provenance. A package replacement deactivates omitted skills. Revoke atomically deactivates that origin and sets all its saved choices off; retain bodies/identities. Reinstall does not silently restore access. No plugin process or signatures verifier in these slices.
- **Freshness:** every changed transaction increments one catalogue revision. Mutations compare the caller's revision inside their transaction; an old editor cannot overwrite a newer choice. Reads are bounded; resolution is one snapshot, returning metadata, not all bodies. Later launch code must recheck revision/grants before publishing a complete view. Changes take effect at the next provider start/resume; current runs keep their installed version. The later plugin framework owns stopping/reloading running consumers at uninstall.
- **Recovery:** immutable bodies, heads, provenance and assignments all live in SQLite and follow its checkpoint/restore, with no registry sidecar. Generated home views remain disposable. Additive migration leaves old rows unchanged, rolls back as a unit on interruption, and extends the exact table/reset/upgrade inventories. An older build follows existing newer-database refusal/recovery behavior. Slice 2 tests old-workspace upgrade, persistence, injected interruption, restore/return and lineage refusal without launching providers or reading real homes.

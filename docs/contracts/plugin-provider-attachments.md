# Live plugin attachments

The supervisor owns one broker per live installation and operational epoch. A workspace receives scoped agent routes through its authenticated supervisor lease. The route command accepts a workspace projection identity, an agent incarnation and occupied server names; it accepts no person operation, executable, endpoint or downstream credential. The workspace identity derives from the canonical workspace path used by the lease. Expired leases and stale lifecycle projections cannot admit discovery or calls.

The lifecycle controller exposes a private view of admitted verified packages and ready connections. Person and agent consumers share one reconciled workspace projection, with separate detach handles. Lifecycle denial revokes broker admission before asynchronous cleanup. The bridge retains route cleanup and broker quiescence obligations; closing an HTTP stream does not prove the plugin or browser exited. The lifecycle host still owns process-exit proof.

The current curated binding supports Chrome. Its tool inventory comes from the verified running package and is checked against the host's reviewed tool names. Resource claims use the manifest's declared read/write bounds. At dispatch the private Chrome policy port resolves tab ownership, checks the current enabled profile and settings/extension choices, and then forwards the tool. Chrome also rechecks those choices inside its own execution queue. Metadata operations retain the package's existing rules. Unknown resource semantics or unsupported plugins remain unavailable rather than receiving an unchecked binding.

`RuntimeHost` supplies an attachment source for fresh starts and resumes, including agents without an external-server grant. Each source has a new incarnation. Discovery is bounded to 1.5 seconds and failures leave ordinary provider work available. Routes are read again before each turn, and names colliding with the app or the person's external servers are omitted without replacing those servers. Closing the source retires its incarnation; a late request cannot reacquire it.

Claude refreshes through the SDK's dynamic MCP API, retaining the app's own server and the person's external servers. Codex has no per-thread MCP configuration update: its running-thread resume path ignores config overrides. A changed attachment set therefore prepares a resumed handle for the same provider ref between turns, then closes the old idle handle only after the replacement succeeds. Revision-only or ordering changes do not reopen a session. It carries current model, effort, approval, plan and folder settings, requests cancellation if a resume exceeds sixty seconds, and keeps the old handle and inventory if that resume fails. A fixed unavailable notice is emitted once, and replacement is retried at the next turn boundary. Cancellation and close join the owned operation; a timeout is never treated as proof of process exit. No refresh reopens a session in the middle of a provider turn. Provider homes and the external-server registry are unchanged.

Scoped capabilities, private plugin credentials and person authority remain separate. Only scoped route descriptors reach Electron and the providers. Errors and attachment diagnostics use fixed outcomes and approved failure words; raw provider or plugin exceptions are not attachment diagnostics.

Production remains unavailable until a real verified rollout plan and catalogue are supplied. No demonstration key or catalogue is injected. Local controls use fictional workspaces and inert server/provider peers. Native provider verification is a separate sealed check outside the product tree.

Managed resumes retain every allocated candidate and retired handle until teardown and its exit fact are proven. The aggregate is stable across swaps, and RuntimeHost owns it through the existing bounded stop and quit drain. An unproved retirement prevents another replacement, while ordinary turns keep using the current handle. An absent or rejected fact never means a process is gone. Codex supplies a stronger witness when its existing group/tree cleanup can prove quiescence; a leader exit or cleanup deadline alone cannot settle it. POSIX cleanup can observe a late group exit without sending further signals. An uncertain Windows tree reading remains unproved.

An internal resume-allocation notification retains cleanup ownership even when the handshake fails before returning a session handle. Successful plan-mode requests cache the canonical never/planning/left launch pair, and rejected requests leave the previous pair intact.

A setting changed during managed preparation invalidates that candidate. The current handle keeps the next turn; a later boundary retries with the successful settings. An unresolved setter defers replacement without delaying ordinary turns. Rejected settings are not carried into a later resume. Windows cleanup credits only a process-table reading incorporated into its cleanup targets; a reading that arrives during the final leader wait cannot prove descendants have stopped.

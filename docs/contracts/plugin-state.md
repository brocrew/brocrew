# Global plugin state, format 1

This is the storage-only part of section 5 of `plugins.md`. It starts no process, installs no package, changes no workspace DB or Skills store, and exposes no IPC/UI/provider-home API. The later authenticated person-command controller supplies consent and verified release metadata; these data methods do not authenticate a person or authorize plugin execution.

## Location and authority

The app must explicitly supply its per-user global plugin root (`<appData>/@brobot2/plugins`) and the known workspace roots. There is no live-root or workspace fallback. Both the global root and every supplied workspace are resolved with realpath before placement is checked; directory identities are also compared along the global ancestry for case aliases. A root inside a supplied workspace, including through a workspace symlink alias, is refused. An unresolvable workspace is refused before root creation. `GlobalPluginState.create` creates a new private root exclusively; `open` requires the existing lifecycle history. Missing/corrupt history is never initialized as empty.

Three folders belong to this store:

- `lifecycle-guard/` is **kept current, excluded from every global and workspace restore set**. It contains an append-only checksummed, hash-chained journal. Its complete history preserves canonical workspace projection receipts keyed by workspace UUID and plugin ID, operation IDs, exact structured consent, installation identities, lifecycle floors, removed markers and release pins. There is no compaction or deletion API.
- `resolution-reservations/` is kept current with the lifecycle guard, outside restore sets. Each operation has a private folder named by its operation ID, containing its prewritten prepare/complete/abort journal records and publication seals. Files are immutable while live. On open, before prepare and after either preparation refusal or resolution, reclamation removes unadmitted and resolved reservation folders. The pending operation's folder and both possible snapshots are preserved.
- `activations/` contains immutable, checksummed activation snapshots. Only `exportActivation()` returns backup/restore data. Reclamation removes unused outcomes and pre-admission orphan snapshots, retaining every snapshot referenced by a journal completion plus both outcomes of the pending operation. A journal completion names exactly one snapshot by file name and SHA-256; a missing, unreadable or mismatching snapshot disables admission. An older snapshot cannot replace the lifecycle guard.

Journal order is contiguous numbered records with a previous-record hash. Each also has an immutable zero-byte tail-loss seal naming its sequence and digest: deleting only the final record is detected rather than rolling the floor back. A missing seal is completed only from an already validated chained record, without activating anything beyond that record; a seal without its record refuses recovery. A private `writer-lock.sqlite` file uses the existing SQLite dependency solely for kernel-backed `BEGIN EXCLUSIVE` exclusion, without tables or data writes. All journal repair, publication and reclamation share this fence. One main-thread process registry, keyed by bigint device/inode, shares exactly one raw validation descriptor and one SQLite connection across all instances and module copies. Busy opens only retain/release that holder: they never open or close another descriptor on the lock file. Reference counting defers connection closure and then raw-descriptor closure until the last reference and active/queued lease are gone. This avoids the POSIX close-any-descriptor lock cancellation hazard. A competing process gets a typed busy refusal; process exit releases the kernel lock without PID or stale-lock guessing. The lock file is no-follow opened, owner/identity checked and held by the shared holder. The trusted private-folder assumptions still apply to SQLite opening the same pathname. No other process may be preparing artifacts while reclamation runs. `store.withExclusive(async callback)` supplies FIFO asynchronous ownership across awaits; synchronous methods remain synchronous and reentrant only for that instance in the owning async context. Unrelated synchronous callers refuse busy. Async callers outside the owning context queue; awaiting a different instance from inside the current lease refuses busy rather than deadlocking its own release. Exclusive hardlink publication remains a compare-and-append fence: competing writers can lose a race but cannot overwrite a published record. Record bodies and envelopes use strict UTF-8 JSON and closed schemas, with size and checksum checks. Checksums detect corruption, not a malicious computer user rewriting their own entire private history.

## Operations

`prepare({operationId, consent, snapshot})` records the exact bounded consent before the installer may mutate anything. Consent is `{action, pluginId, at, expectedSequence, expectedInstallId, release}`, where action is `install`, `update`, `uninstall` or `global-restore`. Release references pin version, downloaded archive SHA-256, manifest SHA-256 and data schema. Restore carries the exported activation snapshot instead of a release. The timestamp is supplied by the person-command controller; the state rule has no wall-clock dependency. Unknown fields are refused. A new optional `workspaces` array on the operation request freezes a unique cohort of at most 64 workspace UUIDs for install/uninstall only. Empty projection receipts for this cohort are reconstructed atomically from the prepared identity and resolution: install completion records them; abort or uninstall resolution clears them. No follow-on record is needed. The full prepare/resolution encoded-byte and publication-name checks therefore cover the whole lifecycle receipt transaction. Older completed format-1 requests without this field remain readable.

Before admitting prepare, the store reserves the next resolution record, its maximum encoded journal bytes, and publication names. Both possible activation snapshots and complete/abort journal records and seals are durably written first. The prepared record binds their exact references and budgets. Capacity refusal happens before a pending barrier is entered. Preparation then persists the allocation and sets a pending barrier. No projection/admission is available while an operation is pending. One pending operation serializes metadata changes across all plugins; stale expected revisions and mismatching retries refuse. Repeating an operation ID with the identical request returns its original allocation, including after a restart or completion. Changing its consent refuses.

`complete(operationId)` verifies its already-published activation snapshot and atomically publishes its prewritten journal completion and seal. Abort uses the corresponding prewritten outcome. Resolution needs no new staging file, activation file or reservation folder; retries and reopen retain the same reserved files and budgets. Physical storage failure or corruption still refuses safely. Completed older format-1 history remains readable; an older pending record without a reservation refuses recovery rather than promising resolution capacity. This code proves only storage state: before calling it, the future controller must perform the contract's readiness, drain, stop/exit and consent checks. It must not treat a prepared allocation as access. A crash after either publication can resume the same operation; it cannot mint another installation or admit a half-written snapshot. `abort(operationId)` is an idempotent denying compensation while the exact pending operation remains current; it marks the affected installation removed instead of reviving prior state. Recovering its executable/data cleanup is a later installer responsibility.

Every fresh Install, including reinstall after uninstall/abort, allocates a never-reused `installId` and activation `incarnation`. Update preserves `installId` and `configRevision`, advances `releaseRevision` and lifecycle sequence, and allocates another incarnation. This slice has no configuration mutation API. Changes of data schema are refused; migration/rollback proofs belong to later slices. All allocated identities remain in the kept-current history and reuse is refused. Uninstall records the removed floor at preparation, before later revocation/cleanup, and retains it after completion. Aborted/removed releases also retain their digest pins; changing bytes for the same plugin/version refuses.

## Receipts and restore

`emptyProjection(workspaceId, pluginId)` returns null for unavailable plugins, or a data receipt binding global-root identity, workspace identity, installation identity, activation incarnation, lifecycle sequence, release/config revisions and operational epoch. Its `skills` and `bindings` are empty. The caller persists it in the existing workspace DB and rechecks the current global state before later admission. This method does not write that DB, ingest skills, select services or grant tools. `matchesProjection` compares against fresh global state and rejects forged, nonempty or stale receipts. The future broker must additionally authenticate the workspace/agent and fence each execution.

`reconcileProjection` returns an explicit revocation plus a new empty receipt, with selection policy `off` across a different installId; within one installation it permits preserving surviving selections. Applying that policy to the single existing Skills store is later integration work. Old bindings must be revoked even when surviving selections can be preserved.

Global restore is journaled and denying before the caller drains all workspaces. Completion retains every lifecycle floor and filters the supplied snapshot against the **current exact** active installation records. Removed A never returns. If B replaced A, an A snapshot cannot guess B's missing metadata/configuration: B remains unavailable until explicit repair. An unrelated later install cannot silently reactivate that excluded B. Compatible restored entries keep installation identity but get a fresh global operational epoch; all old workspace receipts/auth epochs become stale. Aborting restore also rotates the epoch and admits nothing. A snapshot from a different global root is refused. Workspace restore never mutates this global journal.

`projections(workspaceId)` reads canonical receipts from this global journal. `recordProjection(workspaceId, pluginId, receipt)` appends a checked `projected` event or removes that workspace's receipt with a null event. Non-null receipts must match the current exact active installation and global epoch. Projection writes refuse while any lifecycle resolution is pending; they never consume its reserved completion record. They share the journal's writer fence, checksums, seals and capacity bounds (at most 4,096 non-null projection keys, also subject to the 4,096 total record bound). They are excluded from activation exports and all restore sets. Offline receipt obligations remain current until the lifecycle controller reconciles their workspace on reopen. No workspace database table is created.

## Disk safety and limits

The initial disk backend supports POSIX owner-only folders on the main thread. Worker-thread disk access refuses with typed unsupported before opening any storage descriptor, so separate isolates cannot create another process-local lock holder. The pure state machine remains usable in workers. Windows disk storage fails closed before any write; adding an ACL/reparse-aware backend is separate work. The pure lifecycle and receipt formats remain platform independent. No ACL program, shell or supervisor is started here.

The explicit parent and all store folders must be owner-only, actual directories. The parent must be canonical; a supplied symlink alias is refused. Held directory descriptors and bigint device/inode pins are checked around file operations. Files use exclusive owner-only creation and `O_NOFOLLOW`; reads validate regular-file type, ownership, permissions, size and identity. Hardlinked input is refused unless its only second link is provably this store's private interrupted publication stage or its exact immutable reservation counterpart. This proof precedes reading bytes. Publishing an existing target never follows, truncates or replaces it.

Each stage is written and fsynced before atomic exclusive publication; its containing directory is fsynced before success. Ordinary completed publication removes only that operation's verified stage. Interrupted stages inside the lifecycle guard remain inert and are never swept or replayed. Reservation and activation stages are reclaimed under the writer fence after the journal has been validated; only unreferenced artifacts are removed. Deletions validate private regular files and identities, refuse links/reparse paths, and fsync the containing directories. An interrupted reclamation can resume on the next open. Live reservation publication hardlinks are proved before reads; removal of a resolved source leaves the immutable journal link intact. Identity rechecks are not a claim that path-based I/O defeats an adversary running as this same computer user. The app continues to trust the path above its explicitly private parent, as it does for its other data.

Limits: 128 KiB per encoded record/snapshot, 4,096 journal records, 32 MiB total journal bytes, 200 plugin floors subject to record bounds, and at most 8,192 names per storage folder including interrupted stages. Hitting a limit refuses another write rather than forgetting floors or truncating history. Future compaction must preserve all current identity/tombstone floors and immutable release pins; none is implemented here. Filesystems without the required no-follow, hardlink or durability operations fail closed.

Errors contain only approved section 6 wording (`Plugin recovery is required. Open Plugins.`, `Plugin busy. Try again.`, `Plugin unavailable. Try again.`), never raw filesystem errors, paths, causes, credentials or configuration bodies.
